# Loop-Driven Development System — Design Spec

## [S1] Problem

MDH 已有 Loop Engineering 系统（`orchestrator/src/loop/`），能通过 10 个场景覆盖 9 个子系统，31 轮迭代达到 10/10 全通过。但当前系统存在局限：

1. **只有 pass/fail**：无法量化质量差异（一个勉强通过和完美通过的场景得分相同）
2. **手动迭代**：每次发现问题后手动分析、手动改代码、手动重跑
3. **Prompt 盲改**：修改 coordinator/reviewer prompt 后不知道是否真的变好了
4. **场景固定**：10 个场景无法覆盖 MDH 所有能力边界
5. **无回归保护**：改了 A 模块可能破坏 B 模块，没有自动检测

## [S2] Solution Overview

构建 **Loop-Driven Development System**，一个外部于 MDH 的开发方法论系统。通过 4 个子模块形成闭环：

```
跑场景 → 收集指标 → 分析弱点 → 进化 prompt/代码 → 重跑验证
```

与现有 loop 模块的关系：
- **保留** `orchestrator/src/loop/` 作为执行引擎（跑场景、收集原始数据）
- **新增** `loop-engineering/` 作为分析+进化引擎（读取执行结果，驱动优化）

技术选型：TypeScript，SQLite 存储指标趋势。

## [S3] Metrics Module — 量化质量追踪

### 指标体系

| 维度 | 指标 | 计算方式 |
|------|------|----------|
| **完成度** | 任务完成率 | `meeting_ended 收到 / 总场景数` |
| | 文件验收率 | `实际创建文件 / 期望文件数` |
| | 测试通过率 | `通过的 verifyCommand / 总 verifyCommand` |
| **效率** | 平均耗时 | 每个场景的 `duration` |
| | Token 消耗 | 从 LLM 响应估算 |
| | 工具调用次数 | `tool_call` 事件计数 |
| **协作质量** | Agent 参与度 | 参与的 agent 数 / 配置的 roles 数 |
| | 讨论充分性 | 是否经历 `discussing` 阶段 |
| | 审查有效性 | reviewer 是否给出具体建议 |
| **代码质量** | 生成代码行数 | `read_file` 结果长度 |
| | 测试覆盖率 | verify 输出中的 coverage 指标 |
| | 错误处理 | 是否有 try/except、边界检查 |

### 质量分数计算

每个场景的综合质量分（0-100）：

```
score = 完成度(40%) + 效率(20%) + 协作质量(20%) + 代码质量(20%)

完成度 = files_created/files_expected * 20 + test_pass_rate * 20
效率 = max(0, 20 - duration_ms/10000)  // 超时扣分
协作质量 = agents_participated/agents_expected * 10 + has_discussion * 5 + has_review * 5
代码质量 = has_error_handling * 10 + has_tests * 10
```

### 数据库 Schema

```sql
CREATE TABLE scenario_metrics (
  id INTEGER PRIMARY KEY,
  iteration_id INTEGER,
  scenario_id TEXT,
  passed BOOLEAN,
  duration_ms INTEGER,
  files_created INTEGER,
  files_expected INTEGER,
  test_pass_rate REAL,
  agents_participated INTEGER,
  agents_expected INTEGER,
  tool_calls INTEGER,
  phases TEXT,
  issues TEXT,
  timestamp TEXT
);

CREATE TABLE iteration_summary (
  id INTEGER PRIMARY KEY,
  iteration_id INTEGER,
  total_scenarios INTEGER,
  passed INTEGER,
  avg_duration_ms REAL,
  avg_test_pass_rate REAL,
  avg_agent_participation REAL,
  total_issues INTEGER,
  issues_by_severity TEXT,
  timestamp TEXT
);

CREATE TABLE prompt_versions (
  id INTEGER PRIMARY KEY,
  component TEXT,
  version INTEGER,
  prompt_text TEXT,
  avg_score REAL,
  sample_size INTEGER,
  created_at TEXT,
  active BOOLEAN
);
```

### 回归检测

新迭代的质量分低于基线 10% 以上 → 标记为回归，阻塞合入。

## [S4] Evolution Module — Prompt 自动进化

### 核心流程

```
历史数据 → 分析弱点 → LLM 生成改进 prompt → A/B 测试 → 选择胜者
```

### 组件

**1. PromptTracker** — 记录 prompt→outcome 映射

```typescript
interface PromptOutcome {
  component: string;       // 'coordinator' | 'reviewer' | ...
  promptVersion: number;
  scenarioId: string;
  qualityScore: number;
  issues: string[];
}
```

**2. WeaknessAnalyzer** — 识别 prompt 弱点

读取历史数据，输出结构化弱点报告：

```typescript
interface WeaknessReport {
  component: string;
  failingScenarios: string[];
  lowQualityScenarios: string[];
  specificIssues: string[];
  suggestedFocus: string;
}
```

**3. PromptEvolver** — LLM 生成改进 prompt

把弱点报告 + 当前 prompt + 历史胜出 prompt 喂给 LLM，生成改进版。每次只进化一个组件的 prompt，避免多变量混淆。

**4. ExperimentRunner** — A/B 测试

对同一场景集，分别用旧/新 prompt 跑，对比质量分。

```typescript
interface Experiment {
  id: string;
  component: string;
  oldPromptVersion: number;
  newPromptVersion: number;
  scenarios: string[];
  oldScores: number[];
  newScores: number[];
  winner: 'old' | 'new' | 'tie';
  confidence: number;
}
```

胜出条件：新 prompt 平均分高于旧 prompt 5% 以上，且无回归场景。

### 进化触发条件

- 连续 2 轮质量分无提升（停滞）
- 某个场景连续 3 次失败
- 用户手动触发（`--evolve` 参数）

### 进化优先级

reviewer > coordinator > executor > planner

## [S5] Scenario Module — 覆盖扩展

### 当前覆盖

10 个场景覆盖 9 个子系统：agent-core, meeting, tool-executor, skill, review-pipeline, workflow, dynamic-router, security, fallback。

### 缺失覆盖

| 能力 | 新场景 |
|------|--------|
| 长上下文 | 大项目（10+文件）生成 |
| 错误恢复 | agent 执行失败后重试 |
| 并发 | 多任务并行 |
| Git 操作 | 需要 git commit 的任务 |
| 前端生成 | React 组件、CSS 布局 |
| API 开发 | FastAPI/Flask 端点 |
| 数据库 | SQLite/JSON 存储 |
| 重构质量 | 复杂重构（拆模块、提取接口）|
| 多轮对话 | 用户追问改进 |
| 角色选择 | MDH 自主选角色 |

### 场景生成器

从弱点报告自动生成针对性场景：

```typescript
function generateScenario(weakness: WeaknessReport): Scenario
```

### 场景注册表

```typescript
interface ScenarioMeta {
  id: string;
  name: string;
  subsystem: string;
  difficulty: 'easy' | 'medium' | 'hard';
  tags: string[];
  autoGenerated: boolean;
  source: 'manual' | 'weakness-derived' | 'coverage-gap';
  passRate: number;
  avgScore: number;
}
```

## [S6] CI Module — 自动化回归流程

### 触发条件

| 触发 | 场景 | 运行范围 |
|------|------|----------|
| Pre-commit | 本地开发 | 只跑受影响子系统的场景 |
| Pre-merge | PR 合入 | 跑全量场景 |
| Nightly | 定时 | 全量 + 进化实验 |
| 手动 | `npm run loop` | 全量 |

### CI 门禁

```typescript
async function ciGate(): Promise<boolean> {
  // 硬门禁：无 critical issue
  // 软门禁：质量分 >= 阈值
  // 回归检测：与基线对比，不低于 90%
}
```

### 基线管理

每次 main 分支合并后更新基线（`loop-engineering/baselines/latest.json`）。

### CLI

```json
{
  "scripts": {
    "loop": "tsx loop-engineering/src/main.ts",
    "loop:quick": "tsx loop-engineering/src/main.ts --quick",
    "loop:evolve": "tsx loop-engineering/src/main.ts --evolve",
    "loop:ci": "tsx loop-engineering/src/main.ts --ci --threshold=80"
  }
}
```

## [S8] Phased Implementation

### Phase 1: 指标模块（核心基础）
- SQLite 存储层
- 从现有 checkpoint 收集指标
- 质量分数计算
- 趋势报告

### Phase 2: 场景扩展
- 新增 5-10 个覆盖缺失能力的场景
- 场景注册表 + 元数据
- 场景生成器（从弱点自动生成）

### Phase 3: Prompt 进化
- PromptTracker 记录映射
- WeaknessAnalyzer 识别弱点
- PromptEvolver 调 LLM 生成改进
- ExperimentRunner A/B 测试

### Phase 4: CI 集成
- CI 门禁脚本
- 基线管理
- Pre-commit / Pre-merge hooks

## [S9] Success Criteria

- Phase 1 完成后：能看到每次 loop 运行的量化质量分和趋势图
- Phase 2 完成后：场景数从 10 扩展到 20+，覆盖 MDH 所有关键能力
- Phase 3 完成后：prompt 能自动进化，质量分有可测量提升
- Phase 4 完成后：每次 MDH 代码改动自动触发 loop 验证

# V4.7 → V4.8 迁移指引

**面向**: 外部 iframe 接入方 / bridge 调用方
**版本**: V4.8 (2026-05-28)
**目标**: 完成从 V4.7 到 V4.8 的执行面迁移与自诊断接入

---

## 1. 为什么要迁

V4.8 不是新增命令版本，而是把 V4.7 仍残留的 stub/旧路径收束到真实执行链，并给出封版级验证面。迁移重点有四件事：

- **执行输入统一**：高频执行路径继续向 `target_ref` 收口，`handle_id` 不再应作为新的执行输入
- **自诊断可落地**：`AIAutomation.AntiDetection.JsInjectionCount` 可直接用于检查 `LEGACY_FALLBACK` 是否归零
- **计划执行更严格**：`execute_plan` 的 `navigate` 现在要求等待页面原生加载完成，页面变化后旧 `target_ref` 会被主动失效
- **SSO 登录跳转保护**：bridge iframe 跳转到 SSO / 身份提供商时的 CSP 白名单机制，解决 iframe 登录流程中握手断开问题

---

## 2. 迁移重点速查

| 主题 | V4.7 | V4.8 |
|---|---|---|
| Domain 命令执行身份 | `target_ref` 已是主入口，但仍可能见到 legacy `handle_id` 元数据 | **仅应使用 `target_ref` 发起执行** |
| `execute_plan.navigate` | 可能在页面尚未真正可操作时返回 | **等待原生加载完成后再继续后续 step** |
| 页面变化后的 target 复用 | plan-scope 失效规则不完整 | **旧 `target_ref` 不再允许跨页误用** |
| JS 注入诊断 | 有指标，但需要人工解释 | **明确要求 `LEGACY_FALLBACK` 分桶为 0** |

---

## 3. `handle_id` → `target_ref`

### 总原则

- 新代码只把 `target_ref` 当执行身份
- `handle_id` 只可视为兼容期元数据，不应进入新的 command payload
- 若发现/清单结果同时返回 `handle_id` 与 `target_ref`，执行阶段应只透传 `target_ref`

### 适用命令

- `search`
- `login`
- `fill_form`
- `filter_select`
- `paginate`
- `extract_list`
- `click_button`
- `input_text`
- `wait_for_element`

### 推荐写法

```json
{
  "command": "search",
  "payload": {
    "query": "chromium",
    "target_ref": "ref:12345:7"
  }
}
```

### 不再推荐的写法

```json
{
  "command": "search",
  "payload": {
    "query": "chromium",
    "handle_id": "legacy-search-box"
  }
}
```

## 4. `execute_plan` 语义变化

### `navigate` 变严格

V4.8 中，`execute_plan` 的 `navigate` step 完成条件不再是“已发起跳转”，而是“页面原生加载完成，可以安全进入后续 step”。

这意味着：

- `navigate -> click_button` 不应再依赖固定 sleep 才能稳定通过
- 延迟渲染页面下，后续 step 会等待到页面真正 ready

### 页面变化会失效旧目标

若导航、SPA 路由切换或页面替换导致目标上下文变化，旧 `target_ref` 不应继续复用。接入方应按页面变化重新获取目标。

## 5. JS 注入零计数自诊断

V4.8 推荐将以下指标纳入验收：

`AIAutomation.AntiDetection.JsInjectionCount`

重点检查：

- `LEGACY_FALLBACK` 分桶应为 `0`
- 若非 `0`，说明仍有旧 JS 注入路径未被 native 路径替代

建议排查顺序：

1. 先复现具体命令
2. 再查看 `chrome://histograms`
3. 最后定位是否仍走了 legacy fallback/兼容路径

## 6. SSO / 登录平台跳转保护

如果你的 bridge iframe 内业务系统需要跳转到 SSO / 身份提供商进行登录认证，需要配置 extra allowed origins，否则 CSP 会阻止 iframe 加载非默认 origin 的内容，导致登录流程失败、握手断开。

### 配置方式

```bash
--company-chat-extra-allowed-origins=https://sso.company.com,https://login.company.com
```

### 接入检查清单

1. 确认你的 SSO / 身份提供商的 origin（如 `https://sso.company.com`）
2. 将该 origin 加入 `--company-chat-extra-allowed-origins` 启动参数
3. 生产环境应通过企业管理策略（Policy）配置，避免命令行明文暴露
4. 验证 iframe 可正常跳转到 SSO 页面、完成认证、重定向回 iframe 并重新握手

### 注意事项

- extra origins 只影响 CSP `frame-src` / `child-src` 指令，不影响 `postMessage` origin 校验
- 非 HTTP/HTTPS 的 origin 会被静默忽略
- 详细的协议说明参见 `V4.8_BRIDGE_PROTOCOL.md` 第 11 节

---

## 7. 接入方行动建议

1. 清理所有以 `handle_id` 作为执行输入的调用点
2. 将 `execute_plan` 的后续步骤视为建立在"页面已真实 ready"的语义上，而不是固定等待时长
3. 将 `AIAutomation.AntiDetection.JsInjectionCount` 纳入灰度/回归看板
4. 对页面变化场景显式重新获取 `target_ref`
5. 若业务系统需要 SSO 登录，配置 `--company-chat-extra-allowed-origins`
